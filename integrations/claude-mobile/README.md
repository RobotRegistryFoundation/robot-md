# Claude Mobile (iOS / Android) integration

> **Status:** URL-fetch works today. Custom connector support is a Claude Mobile feature we track but don't control.

Claude Mobile has no local tool execution and (as of 2026-04) no stdio-MCP support. What it *does* have is URL-fetch: paste any public HTTPS URL into a conversation and Claude fetches + reasons over the contents. That's enough to operate a robot declared by a `ROBOT.md` hosted at a public URL.

## The pattern

1. **Host the manifest at a public HTTPS URL.** Any static host works — GitHub Pages, Cloudflare Pages, S3, your own server.
2. **Generate a discovery document** (`.well-known/robot-md.json`) next to it, so future MCP-aware clients can find the manifest automatically. Ship with the CLI:

   ```bash
   robot-md publish-discovery ROBOT.md --url https://my-robot.example.com/ROBOT.md
   # writes .well-known/robot-md.json — copy into your web server root
   ```

3. **In Claude Mobile, paste the URL + a question:**

   > *My robot is declared at* `https://my-robot.example.com/ROBOT.md` *— what can it do and what are its safety gates?*

   Claude Mobile fetches the file, parses the YAML frontmatter + markdown body, and answers from the declared fields. The CLAUDE.md-style prose body (automatically generated by `robot-md init --with-claude-md`) makes the safety posture explicit, which is especially useful on mobile where the agent can't run `/check-safety` directly.

## Hosting options

### Option 1 — GitHub / GitLab Pages (simplest, free)

Push `ROBOT.md` to a public repo, enable Pages, reference the raw URL:

```
https://raw.githubusercontent.com/<you>/<repo>/main/ROBOT.md
```

Works instantly. No custom domain needed.

### Option 2 — Your own subdomain (`my-robot.example.com`)

Use the `robot-md publish-discovery` output to make the manifest discoverable by crawlers + federated registries. Place these three files at the root of any static host:

```
/ROBOT.md
/.well-known/robot-md.json
/CLAUDE.md                    # (optional, a nicely-formatted briefing for Claude Mobile)
```

The discovery JSON includes an SHA-256 of the served manifest so clients can detect tampering.

### Option 3 — The RRF public resolver (when registered)

If you registered your robot with `robot-md register`, your RRN resolves at `https://rcan.dev/r/<rrn>`. Today this returns the RCAN marketing page; a manifest-forwarding version is tracked in `rcan-spec`. Meanwhile, the manifest itself lives at whatever URL you chose in Option 1 or 2.

## What Claude Mobile can and can't do

**Can:**
- Fetch the ROBOT.md + CLAUDE.md from the URL you paste.
- Parse YAML frontmatter + markdown prose and answer questions about capabilities, safety gates, drivers, RRN.
- Reason about whether an operator-requested action matches a declared `hitl_gate`.
- Generate the RCAN INVOKE / STATUS payload JSON you could dispatch from a terminal or another app.

**Can't** (by the platform, not by us):
- Run a stdio MCP server.
- Invoke `validate` / `render` / `doctor_summary` directly. (You get the static view, not the live tool results.)
- Dispatch motion commands on the robot's behalf. (A mobile operator can copy the RCAN payload Claude generates and POST it to the robot's gateway using a terminal or an authenticated companion app.)

## Example session

> **You:** Here's my robot: `https://raw.githubusercontent.com/acme/my-bot/main/ROBOT.md` — what are its safety gates?
>
> **Claude Mobile:** *[fetches, parses]* bob is a 6-DOF SO-ARM101 with an OAK-D camera, RRN `RRN-000000000003`. Safety gates:
> - `destructive` — requires explicit human-in-the-loop authorization.
> - `system` — requires explicit authorization.
>
> Software E-stop at 100 ms (`safety.estop`). Max payload 0.5 kg. Destructive motions and system-scope calls pause for operator approval via the RCAN `AUTHORIZE` flow.

> **You:** Can I ask it to pick up a coffee cup?
>
> **Claude Mobile:** `arm.pick` is declared. Whether it counts as "destructive" depends on the operator's policy — a full cup of hot coffee near electronics is a destructive placement. Your manifest routes this through the `destructive` HITL gate, so the robot will pause for authorization. Want me to generate the RCAN INVOKE payload you'd dispatch from a terminal?

## Why can't the mobile app just talk to the robot directly?

Two reasons:

1. **Authentication.** The robot's `network.rrf_endpoint` expects an RCAN-signed request with the robot's private key. Claude Mobile doesn't have (and shouldn't have) the key material on a phone.
2. **No outbound HTTP from the agent.** Claude Mobile is a reasoning layer only; outbound network calls go through your device's normal browser/app stack, not through the agent's tool layer.

The pattern above — fetch the manifest, reason over declared capabilities + gates, generate payloads for the operator to dispatch — is the right split of responsibilities for mobile.
