## Problem (empirically verified 2026-04-20)

`phase_calibrate_extrinsic` seeds `find_in_depth`'s 60-px search window by projecting `tip_base` through the **current** extrinsic (which starts as `preset_default`). Real hardware run on the SO-ARM101 rig showed:

- Arm tip at ready pose: base frame `(360, -2, 103)mm`.
- Preset-extrinsic projects to camera pixel `(654, 750)` — outside a 720-tall image.
- Actual gripper/arm cluster in 200–800mm depth band: pixel `(755, 179)`.
- **Gap: ~570 pixels**. No realistic `search_radius_mm` closes that.

Every sweep pose returns `confidence < 0.3`, phase returns `failed: 0/6 poses produced usable observations`. Calibration subsystem is dead on rigs whose camera mount differs significantly from the canonical `(400, 0, 300) → (200, 0, 0)` tripod the preset assumes.

## Three candidate fixes

| Approach | What it does | Cost | Risk |
|---|---|---|---|
| **A. Motion-delta bootstrap** | Capture frame 0 at pose 0, frame 1 at pose 1. Diff the depth frames. The largest-delta region is the moving arm (gripper tip has the greatest moment arm, so largest motion). Use that centroid as the pose-1 observation. For pose 2+: refine with accumulating extrinsic. | ~150 LOC + tests. 2-3 hr. | Depth noise could contaminate the diff. Needs a motion threshold + min-cluster-size. Also: forearm moves alongside gripper; need to pick the far-from-base cluster. |
| **B. Colored-fiducial** | Operator tapes the gripper tip with a distinctive color (orange). Phase uses existing HSV detector with those params. No projection needed — HSV finds the tape wherever it is. | ~50 LOC. 1 hr. | Requires physical user prep. Contradicts user's original brainstorm pick (option c: "depth-geometry only, no marker"). Works, but the UX regresses. |
| **C. Interactive seed** | Phase captures one frame, displays it, asks operator to click the gripper tip. Uses that pixel as the bootstrap guess. One-time human-in-loop at sweep start. | ~80 LOC. 1.5 hr. Requires a display/UI — probably fails in headless/TTY init. | Degrades non-interactive init further; the whole reason v0.7 auto-calibrates is to avoid human input. Not aligned with zero-friction-first memory. |

## Recommendation: A (motion-delta)

Rationale:
- Preserves the user's original design intent (no marker, no user input during sweep).
- The failure mode of the diff (picking forearm instead of gripper) is *consistent*: every pose will pick the same arm segment, so the solved extrinsic is biased by a fixed tool-frame offset, which is recoverable by later hand-eye refinement. Users who need sub-mm pick accuracy can add a `calibrate --refine-with-tape` verb in v0.8.
- The depth-diff primitive is reusable for v0.8 visual-servoing (descent-time refinement also compares consecutive frames).

## Shape of the implementation (A)

- `gripper_silhouette.find_via_motion_delta(depth_prev, depth_curr, K, min_cluster_px=50) -> (centroid_mm, confidence)` — new function.
  - Compute `abs(depth_curr - depth_prev)` with `cv2.absdiff` (uint16 → float).
  - Mask: `delta > MOTION_THRESHOLD_MM` (e.g., 15mm).
  - Connected components; pick the one with largest area *and* farthest from the bottom-center of the frame (proxy for farthest-from-base).
  - Back-project centroid with median in-band depth.
- `phase_calibrate_extrinsic`: swap `find_in_depth(depth, K, tip_cam_guess, ...)` for `find_via_motion_delta(prev_depth, depth, K)`. Track `prev_depth` between poses.
- First pose has no `prev_depth`: skip detection on pose 0, only use it as baseline for poses 1+. Solver needs ≥3 samples so we still have 5 valid poses from 6.
- Fallback: if motion-delta yields <4 samples (e.g., arm didn't move enough between poses), retry with the existing preset-projection path. Logged as degraded mode.

## Tests

- Synthetic: two depth frames differing only in a 50×50 block moved by 50 px. Asserts correct centroid recovery.
- Synthetic: noisy depth frame (gaussian σ=5mm). Asserts correct centroid despite noise.
- Hardware (opt-in): full sweep against the dev rig. Assert residual < 15mm (looser than v0.7's 10mm because motion-delta is less precise than an ArUco marker would be).
