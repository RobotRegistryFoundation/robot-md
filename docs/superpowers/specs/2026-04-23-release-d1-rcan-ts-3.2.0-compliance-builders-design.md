# Release D1: rcan-ts 3.2.0 compliance builders

**Date:** 2026-04-23
**Status:** Approved for plan-writing
**Tracking tasks:** #220 (this), #221 (D2 deferred)

## Context

Release B (rcan 3.1 consolidation, 2026-04-23) noted `rcan-ts compliance builders (§22-26) — future 3.2.0 when a TS consumer needs them`. Release C (opencastor 2026.4.23.0 RCAN 3.0 alignment) closed the ecosystem drift loop but left compliance surface in TS unbuilt.

Release D opens two coupled but separable follow-ups:
- **D1 (this spec)** — port rcan-py's 4 compliance builders to TypeScript so rcan-ts has SDK-level parity for §22-26 artifact generation.
- **D2 (separate future spec)** — add RRF compliance intake endpoints that consume signed artifacts built with D1. Bob (Raspberry Pi 5 + OpenCastor) is the first planned production producer.

Motivation to do D1 now even without D2 live: D2's endpoint API needs to be designed against a real producer — Bob's opencastor runtime pushing real signed artifacts. Having D1 shipped first lets opencastor start emitting compliance documents and surfaces the actual wire-format edge cases that should shape D2's intake API.

## Critical finding (pre-spec)

`rcan-ts/src/compliance.ts` (141 lines) already ships **type interfaces** for §22-26 — but the §23-26 shapes predate Release B's cross-language byte-parity work and **do not match what rcan-py's `build_*` functions actually emit**. Example: `rcan-ts` `SafetyBenchmark` is `{protocol, score, pass_count, fail_count, run_at, rrn}`, but `rcan.build_safety_benchmark` output is `{schema, generated_at, mode, iterations, thresholds, results, overall_pass}`. Per Release B memory, no TS consumer is using the old types yet. Clean-slate rewrite is acceptable.

The §22 `FriaDocument` / `FriaSigningKey` / `FriaConformance` types appear structurally correct against rcan-py's `FriaDocument` dataclass; they stay.

## Scope

**In scope** (one release cycle, one rcan-ts publish + one rcan-spec commit):

- **rcan-spec** — `fixtures/compliance-v1.json`: 8 cases (2 per builder) with `{name, builder, input, expected_output, expected_bytes_base64}`. Generated by running rcan-py 3.1.1's builders against canonical seed inputs.
- **rcan-ts 3.2.0** — replace §23-26 types in `src/compliance.ts` with rcan-py wire shapes; keep §22 types; add 4 builder functions; re-export 10 spec constants; update `src/index.ts` exports; add tests; bump version + CHANGELOG.

**Out of scope (reject any task that drifts into these):**

- Adding `build_fria` to rcan-ts. rcan-py has no such builder (only the `FriaDocument` dataclass). Wait for upstream.
- Compliance-specific signing helpers. Docs sign via the existing generic `signBody(kp, doc, ...)`; callers do their own canonicalize + sign.
- Any rcan-py, opencastor, robot-md, robot-md-mcp, or RRF code changes.
- RRF compliance intake endpoints — D2, separate brainstorm.
- Fixing rcan-ts's stale CLAUDE.md (known follow-up, dedicated refresh).
- Validating severity strings against `VALID_SEVERITIES` at the builder level (rcan-py ignores unknown severities silently; mirror that).

## Architecture

One rcan-ts package release + one rcan-spec config commit. No new SDK primitives (reuses existing `canonicalJson`, `signBody`), no wire format changes (by construction — fixture enforces byte parity with rcan-py).

- **rcan-spec** (branch `master`, direct commit): fixture file mirrors the Release B `canonical-json-v1.json` pattern — an array of test cases with expected canonicalized bytes. Authority for cross-language byte parity.
- **rcan-ts 3.2.0** (branch `main`, tag `v3.2.0`, npm publish via OIDC): `src/compliance.ts` expands from types-only (~141 lines) to types + builders + constants (~450 lines expected).

**Release sequencing:**
1. Wave 0: commit fixture in rcan-spec master.
2. Wave 1: bundle fixture copy into rcan-ts `tests/fixtures/`, implement builders, tests green.
3. Wave 2: bump package version + CHANGELOG, publish via tag push.

**No cross-repo dependencies on D2.** D2 consumes D1 later but doesn't gate D1's ship.

**Version bump:** 3.1.1 → **3.2.0** (minor). Additive builder surface is the dominant story. §23-26 type replacements are technically breaking, but no TS consumer uses them (per Release B memory); the minor bump telegraphs "new surface" to anyone watching.

**Fixture generation script** (not committed — one-shot):
- `scratch/gen_compliance_fixture.py` (run from any venv with `rcan==3.1.1` installed):
  - For each seed input, calls the corresponding `rcan.build_*` function, captures the output dict, runs `rcan.canonical_json(output)`, base64-encodes the bytes, assembles the case.
  - Prints JSON to stdout; human redirects to `fixtures/compliance-v1.json` and commits.

Sanity gate before commit:
```bash
python3 -c "
import base64, json, rcan
f = json.load(open('fixtures/compliance-v1.json'))
for c in f['cases']:
    got = rcan.canonical_json(c['expected_output'])
    expected = base64.b64decode(c['expected_bytes_base64'])
    assert got == expected, c['name']
print('all 8 cases: expected_output canonicalizes to expected_bytes_base64')
"
```

## Error handling + risks

**Accepted semantics (mirror rcan-py exactly):**
- Unknown severities in `buildIncidentReport.incidents[*].severity` silently ignored (no throw, no count). Matches rcan-py behavior locked by the Release C "unknown severity ignoring" test case.
- `buildEuRegisterEntry` fills `conformity_status` and `submission_instructions` defaults from re-exported constants when kwarg omitted or `undefined`.
- No runtime input validation beyond what TypeScript's type system enforces at compile time (no "required field missing" guards — dead weight for typed consumers).
- `generated_at` is a plain string — not validated as ISO-8601 at the builder layer. rcan-py doesn't validate either.

**Byte-parity risks:**
- **Number formatting drift** — Python `1.0` vs JS `1` serialization. Mitigation: prefer integer seed inputs in the fixture; if a float is required, verify byte parity during Wave 0 generation and adjust canonical JSON handling if needed.
- **Unicode in strings** — fixture MUST include at least one non-ASCII character (e.g., in provider name) to prove canonical JSON's `ensure_ascii=False` parity between Python and TS.
- **Key ordering** — canonical JSON sorts keys, so the builder's returned dict ordering doesn't affect canonicalized bytes. But raw dict equality tests can fail; tests must compare canonicalized bytes, not `JSON.stringify(output)`.

**Release sequencing risks:**
- **Fixture version drift** — if rcan-py ever changes a builder's output shape, both the rcan-spec fixture AND rcan-ts must update together. Mitigation: fixture's top-level `rcan_py_version` field records the baseline; CI in rcan-spec can assert any fixture regeneration script runs against a pinned rcan-py version.
- **Bundled fixture drift in rcan-ts** — if the rcan-spec fixture updates, rcan-ts's bundled copy goes stale silently. Mitigation: `tests/check-fixture-drift.test.ts` (optional, low-priority; document in CHANGELOG notes) compares the bundled fixture's sha256 against the canonical. For 3.2.0 ship, bundle once + document the canonical path.

**Rollback posture:**
- rcan-ts 3.2.0 bug → publish 3.2.1 with fix. Don't un-publish.
- rcan-spec fixture is append-only in spirit (v2 file for additions; v1 fixture frozen).

**What could go wrong not covered:**
- An unknown TS consumer using the old §23-26 types breaks on upgrade. Per Release B memory, no such consumer exists. Risk accepted.
- D2 / Bob's opencastor later emits a custom field our builders don't produce. That's D2's problem; D1 ships the rcan-py-equivalent surface, no more.
