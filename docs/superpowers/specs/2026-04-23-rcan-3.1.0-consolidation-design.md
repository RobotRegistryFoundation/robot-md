# rcan-py 3.1.0 + rcan-ts 3.1.0 — consolidation release (design)

**Status:** Design approved (2026-04-23). Implementation pending.
**Scope boundary:** rcan-py, rcan-ts, rcan-spec, robot-md, RobotRegistryFoundation. Opencastor NOT touched.
**Budget:** 3–4 sessions across 4 deploy waves.

---

## Motivation

Ecosystem audit (2026-04-23) found that robot-md 1.0.0 and RRF 1.10.0
both reimplement primitives that should live in the SDKs:

1. **`canonical_json` duplicated three ways.**
   - robot-md `cli/src/robot_md/signing.py:114-118` — Python impl
   - RRF `functions/_lib/verify.ts:21-23` — TypeScript impl
   - rcan-py `rcan/firmware.py:97` — private method, not exported at
     module level

2. **`sign_body` / `verify_body` not in either SDK.**
   - robot-md reimplements both in `signing.py:121-168`, wrapping rcan-py's
     low-level `sign_hybrid(message: bytes)` + `verify_hybrid()` with the
     dict-level contract that both robot-md and RRF actually need.
   - rcan-py + rcan-ts expose hybrid signing at the bytes level only.

3. **§22–26 compliance schemas are dataclass-only in rcan-py.**
   - rcan-py `rcan/compliance.py` defines `FriaDocument`, `SafetyBenchmark`,
     `InstructionsForUse`, `PostMarketIncident`, `EuRegisterEntry` as
     frozen dataclasses with NO builder functions.
   - robot-md reimplements all four builders:
     `benchmarks.py:41` (§23), `ifu.py:32` (§24),
     `incidents.py:31` (§25), `eu_register.py:28` (§26).

`feedback_rcan_spec_authority.md` mandates: "Fix upstream first; no
shims in downstream consumers." The current duplication violates this.

---

## Architecture

rcan-py + rcan-ts become the authoritative home for canonical JSON
serialization and dict-level hybrid signing. All downstream consumers
(robot-md, RRF) delete local copies and import from the SDK. A shared
`canonical-json-v1.json` fixture in rcan-spec pins byte-level output of
both SDKs.

```
                    rcan-spec
                         │
                         │ fixtures/canonical-json-v1.json
                         │ (single source of truth)
                         ▼
         ┌───────────────┴───────────────┐
      rcan-py 3.1.0                 rcan-ts 3.1.0
      ├─ rcan/encoding.py           ├─ src/encoding.ts
      │   canonical_json()          │   canonicalJson()
      ├─ rcan/hybrid.py             ├─ src/hybrid.ts
      │   sign_body()               │   signBody()
      │   verify_body()             │   verifyBody()
      ├─ rcan/compliance.py         │   (no compliance builders — YAGNI)
      │   build_safety_benchmark()
      │   build_ifu()
      │   build_incident_report()
      │   build_eu_register_entry()
      ├─ rcan/__init__.py           ├─ src/index.ts
      │   re-export all new API     │   re-export all new API
         ▼                               ▼
      robot-md 1.0.1                 RRF deploy
      ├─ signing.py: delete          ├─ verify.ts: delete
      │   canonical_json,            │   canonicalJson, verifyHybrid
      │   sign_body, verify_body     │   (import from rcan-ts)
      ├─ benchmarks/ifu/incidents/   │
      │  eu_register.py: delete      │   (swap import only)
      │   build logic
```

**What stays in robot-md's `signing.py`:** `SigningKeypair` wrapper +
atomic `save_keypair`/`load_keypair` (filesystem keystore —
robot-md-specific, not duplicated upstream).

**What stays in RRF's `verify.ts`:** nothing. File becomes a 2-line
re-export from rcan-ts, or gets inlined at the one register.ts call
site (decide during implementation — trivial either way).

**Non-breaking to existing 3.0 API surface:**
- `rcan/crypto.py`'s `sign_hybrid`/`verify_hybrid` bytes primitives
  remain unchanged. New `hybrid.py` is a thin wrapper on top.
- `rcan/signing.py`'s v2.2-era message PKI is untouched. (Its
  wrong-doctrine "Ed25519 deprecated" docstring is out-of-scope for
  3.1.0; flagged for a future cleanup release.)

## API surface

### rcan-py 3.1.0

```python
# rcan/encoding.py — new, zero crypto dep
def canonical_json(body: dict) -> bytes:
    """UTF-8 bytes of json.dumps(body, sort_keys=True,
    separators=(",",":"), ensure_ascii=False). Deterministic."""

# rcan/hybrid.py — new, depends on rcan.crypto
def sign_body(keypair: MlDsaKeyPair, body: dict, *,
              ed25519_secret: bytes, ed25519_public: bytes) -> dict:
    """Sign body+pq_signing_pub+pq_kid canonically. Returns body + sig."""

def verify_body(signed: dict, pq_signing_pub: bytes) -> bool:
    """Strip sig, re-canonicalize over body+pq_signing_pub+pq_kid, verify."""

# rcan/compliance.py — add build_* functions in-place
def build_safety_benchmark(rrn, manifest_path, results) -> dict: ...
def build_ifu(rrn, manifest_path, ...) -> dict: ...
def build_incident_report(rrn, incidents) -> dict: ...
def build_eu_register_entry(rrn, manifest_path, fria_path) -> dict: ...

# rcan/__init__.py — top-level re-exports
from rcan.encoding import canonical_json
from rcan.hybrid import sign_body, verify_body
from rcan.compliance import (build_safety_benchmark, build_ifu,
                              build_incident_report, build_eu_register_entry)
```

Downstream canonical import: `from rcan import canonical_json, sign_body,
verify_body` — shortest path. Explicit paths (`from rcan.encoding import
canonical_json`) remain supported for consumers who care about origin.

### rcan-ts 3.1.0 (parity subset, no compliance builders)

```typescript
// src/encoding.ts
export function canonicalJson(obj: Record<string, unknown>): Uint8Array

// src/hybrid.ts
export function signBody(
  keypair: MlDsaKeyPair,
  body: Record<string, unknown>,
  opts: {ed25519Secret: Uint8Array; ed25519Public: Uint8Array}
): Record<string, unknown>

export function verifyBody(
  signed: Record<string, unknown>,
  pqSigningPub: Uint8Array
): boolean

// src/index.ts — re-export
export { canonicalJson } from "./encoding.js";
export { signBody, verifyBody } from "./hybrid.js";
```

**Names locked:** Python snake_case (`canonical_json`, `sign_body`,
`verify_body`) matches robot-md's existing local names for zero-friction
cleanup. TypeScript camelCase (`canonicalJson`, `signBody`, `verifyBody`)
matches rcan-ts's existing convention.

## Fixture format

**Location:** `rcan-spec/fixtures/canonical-json-v1.json` (new file).

```json
{
  "format": "rcan-canonical-json-v1",
  "description": "Byte-level invariants for RCAN canonical JSON serialization. Both rcan-py and rcan-ts MUST emit identical UTF-8 bytes for every case.",
  "cases": [
    {"name": "key_ordering",
     "input": {"b": 1, "a": 2, "c": 3},
     "expected_bytes_base64": "<base64>"},
    {"name": "nested_objects",
     "input": {"outer": {"z": 1, "a": 2}},
     "expected_bytes_base64": "<base64>"},
    {"name": "unicode_no_escape",
     "input": {"name": "Café ☕"},
     "expected_bytes_base64": "<base64>"},
    {"name": "no_whitespace",
     "input": {"a": 1, "b": [1, 2, 3]},
     "expected_bytes_base64": "<base64>"},
    {"name": "empty_and_null",
     "input": {"a": null, "b": {}, "c": []},
     "expected_bytes_base64": "<base64>"},
    {"name": "realistic_registration_body",
     "input": {"rrn": "RRN-000000000042", "pq_signing_pub": "<b64>", "pq_kid": "abc12345", "rcn_ids": ["RCN-000000000001"]},
     "expected_bytes_base64": "<base64>"}
  ],
  "invariants": [
    "Keys sorted lexicographically at every nesting level",
    "No whitespace (no spaces, tabs, newlines)",
    "Non-ASCII Unicode emitted as UTF-8 bytes, NOT \\uXXXX escapes",
    "Integers rendered without trailing .0",
    "Empty object rendered as {}, empty array as []",
    "No trailing newline"
  ]
}
```

**How it's built (once, during Wave 1):** dev machine runs a scratch
`canonical_json` implementation on each `input`, base64-encodes output,
writes `expected_bytes_base64`. That locks the bytes. Both SDKs then
assert their output matches.

**Spec text update:** rcan-spec gains a short §27 (or next available
section) describing the invariants and pointing to the fixture as
authoritative.

### Wave 4 — RRF deploy

Depends on rcan-ts 3.1.0 on npm.

- `package.json`: add `"rcan-ts": "^3.1.0"` to dependencies.
- `functions/_lib/verify.ts`: delete local `canonicalJson` +
  `verifyHybrid`. Either becomes a 2-line re-export from rcan-ts, OR
  gets inlined at the one register.ts call site. (Decide during
  implementation.)
- Run `vitest` — existing `register.test.ts` + siblings MUST still
  pass. Cross-language hybrid-fixture tests are the real proof.
- Commit, push to main → Cloudflare Pages auto-deploy.
- Smoke-test: `curl -X POST https://robotregistryfoundation.org/v2/robots/register -d '{}'` expect 400 "Unsigned registration not permitted".

### Why this order is non-negotiable

- Fixture must exist before SDKs consume it.
- SDKs must be on registries before downstream deps can bump.
- rcan-py ↔ rcan-ts within Wave 2 are independent.
- robot-md ↔ RRF within Waves 3/4 are independent; listed serially for
  cognitive load, can parallelize.

### Rollback story

Each wave is its own PyPI/npm version. If Wave 3 breaks, pin robot-md
back to 1.0.0; rcan-py 3.1.0 on PyPI is additive + harmless. Same
dynamic for Wave 4 / rcan-ts.

## Testing strategy

Three layers, in order of what catches what.

### Layer 1 — fixture parity (critical)

Both rcan-py and rcan-ts add a test that iterates every case in
`canonical-json-v1.json` and asserts the SDK's output bytes match
`expected_bytes_base64` exactly. One assertion per case. If either SDK
drifts, its CI goes red immediately.

### Layer 2 — SDK unit tests

- `test_encoding.py` / `encoding.test.ts`: whitespace, key ordering,
  unicode, ASCII escape behavior. Tested independently of fixture for
  clarity of failure mode.
- `test_hybrid.py` / `hybrid.test.ts`: sign_body round-trip,
  tampered-body rejection, missing-ids rejection, wrong-key rejection.
- `test_compliance.py` (py only): each `build_*` returns expected
  envelope shape, sibling IDs round-trip, schema name constants
  (`rcan-ifu-v1`, etc.).

### Layer 3 — downstream integration

- **robot-md 1.0.1**: `cli/tests/test_register.py` and
  `cli/tests/test_signing.py` MUST still pass without test-logic change.
- **RRF deploy**: `functions/v2/**/*.test.ts` MUST still pass against
  rcan-ts's `verifyHybrid`. The cross-language Python-signed hybrid
  fixtures at `functions/_lib/fixtures/*-fixture.json` are the
  authoritative end-to-end check — they prove rcan-py's signed bytes
  still verify via rcan-ts's verifier.

### Not tested

- rcan-ts on browsers (existing browser bundle via tsup unchanged).
- rcan-ts TypeScript compilation on old Node versions — stick with
  existing floor.
- Performance — all changes are pure refactors of existing code paths.

### Pre-tag checklist (each SDK wave)

1. Fixture test green
2. SDK unit tests green
3. `pip install -e .` / `npm run build` succeeds
4. `pypi-publish --dry-run` / `npm publish --dry-run` shows expected
   contents

## Out of scope

Explicitly deferred from 3.1.0:

- **rcan-ts compliance builders.** No TS consumer emits §22–26 artifacts
  today (robot-md is Python-only; RRF stores nothing). Tracked as future
  rcan-ts 3.2.0 work when a TS consumer appears.
- **`rcan/signing.py` doctrine update.** The v2.2-era module declares
  "Ed25519 deprecated" which contradicts RCAN 3.0 hybrid. Needs a
  dedicated cleanup release; not blocking 3.1.0 because `signing.py` is
  untouched by this work.
- **Opencastor RCAN 3.0 alignment.** Separate multi-session release C
  (audit rec #1). Opencastor still rejects `rcan_version: "3.0"` and
  cannot consume ROBOT.md.
- **RRF compliance intake endpoints.** Separate release (audit rec #2).
  RRF still stores no FRIA/IFU/incidents/EU-register artifacts.
