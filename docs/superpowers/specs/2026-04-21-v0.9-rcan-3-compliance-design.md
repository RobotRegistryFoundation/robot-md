# robot-md v0.9 — RCAN 3.0 compliance (design)

> **Status:** Design. Not a plan. Each sub-release below gets its own brainstorm → spec → plan cycle; this doc is the umbrella.
> **Date:** 2026-04-21
> **Supersedes:** the "v0.9 breadth" sketch in `docs/superpowers/specs/2026-04-20-v0.8-v0.9-roadmap.md` §v0.9 — breadth work moves to v1.x.
> **Related:** cross-repo audit performed 2026-04-21 against rcan-spec v3.0 and `craigm26/RobotRegistryFoundation`.
> **Revision 2026-04-21 (pm):** The v0.9.0 Task 1 spike surfaced that rcan-py's `validate_config` expects a full RCAN *config* (with `agent`/`node_type`/`rcan_node_version`), not a ROBOT.md manifest. rcan-spec does not define ROBOT.md as its document type — §17 "manifest" is the `/.well-known/rcan-node.json` endpoint. Per the ecosystem principle "rcan-spec is the authority" (`feedback_rcan_spec_authority.md`), **the second-pass validator idea in v0.9.0 is dropped**. rcan-py is consumed as a *library* for primitives (crypto, version constants, `from_manifest` cross-link) — not as a co-validator of ROBOT.md files.

## Motivation

robot-md 0.8.0 ships declaring `rcan_version: "3.0"` in every shipped manifest (`ROBOT.md` + `examples/*.ROBOT.md`) but does **not** implement the RCAN 3.0 contract. The 2026-04-21 audit found 8 gap categories, headlined by:

- No signing at all. `cli/src/robot_md/register.py:10-14` still describes signing as a "v0.2 will add" future; register POSTs plain JSON.
- Schema was admitting 2.1/2.2.x manifests (fixed in `cf25f6a` prior to this spec).
- `fria_ref` optional-and-nullable; Annex-III gating impossible.
- §23 Safety Benchmarks, §24 IFU, §25 PMM, §26 EU Register fields entirely absent.
- No dependency on `rcan-py`; every 3.0 primitive reimplemented or missing.

The ecosystem policy — "everything depends on RCAN 3.0+ going forward" — requires closing this gap before any further feature work. The fix is a compliance-theme release series.

## Goal

robot-md honestly implements the RCAN 3.0 contract it declares. Success = all criteria below pass, at which point v1.0.0 is tagged as the compliance declaration.

## Success criteria

All must be true for the v1.0.0 tag:

1. Every `robot-md register` submission is signed with ML-DSA-65 + Ed25519 hybrid (via `rcan.crypto.sign_hybrid`); RRF accepts signed payloads and rejects unsigned (per RCAN 3.0 §2.2).
2. Schema requires `compliance.fria_ref` for manifests classified as EU AI Act Annex-III; enforcement runs in `robot-md validate` (using robot-md's own jsonschema — *not* an rcan-py SDK pass).
3. Schema has fields for §23 Safety Benchmarks, §24 IFU, §25 PMM, §26 EU Register; CLI emits them where populated.
4. robot-md accepts and emits RCN/RMN/RHN registry IDs alongside RRN (matching RRF's `/v2/{components,models,harnesses}/` endpoints).
5. `cli/pyproject.toml` depends on `rcan>=3.0,<4.0` — used for crypto primitives, `from_manifest` cross-link, and version constants. **Not** used to co-validate ROBOT.md.
6. Schema `rcan_version` pattern remains pinned to `^3\.[0-9]+(\.[0-9]+)?$` (already done in `cf25f6a`); no 2.x re-admission.

## Cross-cutting decisions (apply to every v0.9.x)

1. **Every v0.9.x sub-release publishes to PyPI.** No batching. Monitor's drift detector (`opencastor-ops/config/repos.json`) gets bumped each time.
2. **Breaking changes are allowed, flagged `feat!:` / `fix!:`.** v0.9 is explicitly a compliance-floor change; 2.x manifests already stopped validating in `cf25f6a`.
3. **CI matrix stays at Python 3.10/3.11/3.12/3.13** unless rcan-py forces 3.11+. If so, drop 3.10 cleanly — no compat shim.
4. **RRF-side changes get their own plan, not bundled here.** If v0.9.1 discovers RRF needs to verify signatures (not just receive them), that's a separate ticket against `craigm26/RobotRegistryFoundation` — we surface the gap during v0.9.1 and open it as a blocker.
5. **Each sub-release has its own brainstorm → spec → plan → execute cycle.** This theme spec is the umbrella.

## Theme-level risks

1. **rcan-py may not ship ML-DSA primitives** despite declaring the `ML_DSA_PRIMARY` feature flag in `SUPPORTED_FEATURES`. The flag may be aspirational. *Mitigation:* v0.9.0's rcan-py spike also greps for `ml_dsa`/`dilithium` in the package. If absent, v0.9.1 must either implement signing directly or file an upstream issue on rcan-py before proceeding.
2. **RRF may not verify signatures.** The audit confirmed RRF *accepts* the signing fields (`pq_signing_pub`, `pq_kid`) but not that it *validates* them. If verification is missing, signed robot-md registration succeeds against an unsigned-accepting RRF — defeating the point. *Mitigation:* v0.9.1 spec includes "verify RRF rejects tampered signature" as an integration test; if it passes on a tampered payload, RRF-side work lands first.
3. **§26 EU Register endpoint may not exist.** Art. 49/60 register is a legal construct; the HTTP endpoint may not be stood up until near 2026-08-02. *Mitigation:* v0.9.4 may ship as "emit the payload + document expected endpoint; post is a `--dry-run` toggle" until the real endpoint exists.
