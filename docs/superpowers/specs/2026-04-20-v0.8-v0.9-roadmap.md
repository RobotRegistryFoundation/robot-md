## Milestone Chain Summary

- **v0.7** (designed) — hardening: reliability, perception accuracy, zero-friction calibration. Closes the hardware-bring-up feedback loop.
- **v0.8** (this doc) — expansion: multi-preset IK, collision, MCP observability, visual servoing. Unlocks robots beyond SO-ARM101.
- **v0.9** (this doc) — breadth: bimanual, LfD, SLAM, mobile bases. Moves beyond single-arm single-rig.

## v0.8 — Expansion

Three buckets: **C** (IK/motion planner expansion), **E** (Agent/MCP surface improvements), **F** (visual servoing).

### C. IK / motion planner expansion (largest bucket; foundational)

**Multi-preset IK.** Current `inhouse-so-arm101` is hardcoded 3-link planar. Promote to a family: `KinematicsSolver` interface with registered implementations; add solvers for:

- `koch_arm` (similar geometry, different link lengths — easy extension of in-house solver).
- `ur5e` (6-DoF standard — use `ikpy` or `pinocchio`).
- `franka_panda` (7-DoF — `pinocchio` or `curobo` if latency matters).

The `physics.solver.ik_provider` preset field already exists and is enum-string today. v0.8 wires more values through and registers the implementations.

**Collision + self-collision.** Introduce `physics.collision.geometry` (list of capsules/boxes per link in tool frame). Trajectory planner runs sampled-collision-check against self and against declared static obstacles. Start with self-collision only; workspace-obstacle checking defers to v0.9 SLAM.

**Side-grasp / non-top-down.** Generalize `plan_pick`: `grasp_orientation: top_down | side_x | side_y | auto`. `auto` chooses based on target height + workspace constraints. Most useful for mug-like objects where top-down doesn't fit.

**Cartesian waypoint caching.** Memoize common trajectories (home→ready, ready→center-workspace) per manifest hash so repeat picks don't re-plan. Not critical but cheap; gates pickup speed improvements later.

### E. Agent / MCP surface improvements

**Recent-errors resource.** New MCP resource `robot-md://<path>/recent_errors` — last N capability invocations with status, reason, recovery_hint. Agents can answer "why did my last pick fail?" without shelling out. Uses the `reason` enum shape that v0.7 already establishes — no new schema work.

**Precondition error verbosity.** Current precondition failures return `{status: precondition_failed, preconditions: [...]}` — add per-precondition `suggested_fix` (e.g., `extrinsic_present` unmet → "run `robot-md calibrate --extrinsic`"). Builds on the structured error discipline from v0.7.

**`discover` tool refinement.** Today it runs declarative pipelines; add streaming progress events over MCP so long-running discovers (multi-second arm motion) report per-step. Uses MCP notifications.

### F. Visual servoing / closed-loop refinement

**Descent-time vision refinement.** During the cartesian descent phase of `arm.pick`, re-query vision every 100ms; adjust target if drift >5mm. Requires vision latency budget <50ms and IK recomputation in loop.

**Grasp confirmation.** After grip-close, read gripper position; if fully closed (no object between jaws), return `status: grasp_failed` rather than proceeding. Requires reading `gripper.open_steps` vs actual steps. Can be done without image feedback.

**Force-feedback placeholder.** STS3215 reports load; define a threshold for "contact made." Useful for placing (stop descent on contact) and for catching mis-picks. Doesn't need new schema — expose the reading.

### Dependencies between v0.8 buckets

- **E depends on nothing** — can ship first as a focused week; could even ship as v0.7.1 if scope allows.
- **F depends on E** (grasp_failed needs the recent-errors resource to report through) and on **C** (descent refinement needs fast IK).
- **C is the long pole** — each new solver is a self-contained chunk, good for parallelization.

### Suggested v0.8 sequencing

1. **E first** (one focused week) — low-risk UX quality-of-life, unblocks observability of the harder work.
2. **C.multi-preset-IK second** (2–3 weeks) — unlocks koch_arm, ur5e, franka_panda actually being pickable robots. Biggest user-value add.
3. **C.collision + F.grasp-confirmation third** (parallel) — safety + reliability.
4. **C.side-grasp + F.visual-servoing last** (most ambitious, benefit from stable base).

### What v0.7 should leave in place for v0.8

- `KinematicsSolver` as a named interface even while only one implementation exists (no rewrite needed in v0.8, just registration).
- MCP error structure stays routable — the `reason` enum from v0.7 is the seed for the `recent_errors` resource.
- Gripper state readable from the motion layer — v0.7 doesn't need to expose it, but shouldn't bury it such that v0.8 grasp-confirmation needs refactoring.

## v0.9 — Breadth

Four buckets; each is a cohesive mini-project. Order is suggestion only — can be resequenced based on user demand.

### Bimanual / dual-arm

Real `aloha2` support: two-arm IK coordination, dual-gripper grasp planning, handoff primitive (`arm.handoff(left, right, target)`), per-arm workspace bounds with shared collision envelope. Biggest schema change: `physics.arms[]` where each arm has its own kinematics + gripper. Capabilities gain `arm: left|right|either` qualifier.

### Learning-from-demonstration

Capture joint trajectories during manual teach-back, replay with parameterization (target object). `learned_skills` top-level (in manifest schema since v0.6.0) finally gets a real producer. New verb: `robot-md teach <skill_name>` → records a demo → saves as a `learned_skills[]` entry with joint-trajectory + target-descriptor binding. Playback via `execute_task(skill=<name>, target=<descriptor>)`.

### Workspace-obstacle SLAM / runtime mapping

OAK-D depth stream fed into a live occupancy map (voxel grid, persisted under `~/.robot-md/maps/<manifest_hash>.vox`); collision planner consults the map instead of (or in addition to) declared obstacles. Clears the "arm knocks into stuff it doesn't know about" failure mode. Requires background scanner process; opt-in.

### Mobile-base integration

Wire capability pipelines for `picar_x`, `turtlebot4`, `unitree_go2` — these presets exist today as schema-only; they don't actuate. Introduces mobile-base kinematics (`nav.goto(x, y, theta)`, `nav.follow(target_descriptor)`), separate from arm kinematics. For robots with both (arm on a base — future), the two systems compose.

### Dependencies

- Bimanual and LfD are independent.
- SLAM depends on v0.8 C.collision (it's the consumer of the new collision geometry).
- Mobile-base is fully independent and the easiest entry point if user demand pulls that way first.
